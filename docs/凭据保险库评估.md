# 凭据保险库评估（D5：AES-GCM 可选保险库模块）

> 状态：已实现为可选模块，**默认关闭**，不改变任何现有凭据路径。
> 实现文件：`packages/dsh-plugin/src/services/vault.ts`；测试：`packages/dsh-plugin/tests/vault.test.ts`。
> 注意：模块在顶层自注册了 workspace 扩展（与 backup/tasks 等服务写法一致），但按任务约束未改动
> `services/index.ts`；正式挂载只需在该文件加一行 `import "./vault.js";`（挂载前后默认行为一致，
> 未显式开启时所有保险库路由返回 403 且不落任何文件）。

## 1. 为什么默认关闭

1. **现有媒体适配器凭据已有归属**：MIMO/Fish Audio 等密钥由 DSH 环境变量（`MIMO_API_KEY`、
   `FISH_API_KEY` 等）或项目外配置决定，参考报告域 4 的结论是“短期无需自建密钥库”。
   保险库若默认开启，会制造第二条凭据路径，反而增加“密钥到底在哪”的心智负担与排障成本。
2. **opt-in 语义可验证**：开关是纯函数 `isVaultEnabled(env)`——仅
   `DSH_MIAOWU_VAULT_ENABLED=1`（严格字符串相等）视为开启。未启用时路由层先查开关，
   直接返回 `403 { error: "凭据保险库未启用…", enabled: false }`，且本次请求不触碰磁盘
   （不断言工作区、不创建 `.oh-story/vault/`、不写密钥），“不落任何密钥数据”由单测覆盖。
3. **零配置契约变更**：插件 `Config`（`editorMaxBytes`/`trustedHosts`）未动；
   keyring、DSH 配置、环境变量读取全部原样。保险库是加法模块，不是迁移。

## 2. 适用场景（什么时候应该开启）

- **未来插件需自管第三方 key**：例如新增的媒体/检索/分析供应商要求插件侧持久化密钥，
  而调用方又不希望把 key 长期放在 shell 环境变量里。
- **跨会话持久化非环境类凭据**：一次性写入后多会话复用（如离线工作区的本地 token），
  避免每次启动重配环境。
- **离线/隔离工作区**：无可信环境变量注入通道时，工作区内自带一份加密存储，
  随工作区目录走（注意备份含义见 §3）。

不适用：已有环境变量覆盖的 MIMO/Fish 密钥**不要**搬进保险库——多一处存放等于多一处泄露面。

## 3. 安全边界与风险

| 项目 | 现状 |
|---|---|
| 加密原语 | AES-256-GCM（`node:crypto`，零新依赖）；随机 12 字节 IV；authTag 校验失败抛错，防篡改；相同明文两次加密密文不同 |
| 密文格式 | `{ v: 1, iv: base64, tag: base64, data: base64 }`，只含密文；**主密钥永不写入任何 JSON** |
| 主密钥 | `.oh-story/vault/master.key`，32 字节 `randomBytes`；不存在时首次写入自动创建，0600/0700 尽力设置（Windows 下 chmod 无效，仅尽力） |
| 最大风险 | **主密钥是本地文件**：拿到 `master.key` 即全泄露。文件权限是唯一防线，无口令/KDF/系统钥匙串兜底 |
| 无 KDF/口令解锁 | 密钥即文件本身；无 PBKDF2/scrypt/argon2，无“忘记口令”概念，删了 `master.key` 旧密文永久不可解 |
| 无远程加密备份 | 保险库随工作区目录走；备份时要么连 `master.key` 一起带走（方便但扩散泄露面），要么只备密文（丢密钥即丢数据），需使用者二选一并记录 |
| 轮换机制 | `POST /oh-story/vault/rotate`：先纯函数全量解密+新钥加密（任一条目失败直接抛、未动盘）→ 临时文件 → 备份旧密钥 → 装新密钥+新库；收尾失败把旧密钥拷回，旧库此前未被改动，回滚后旧密钥保持可解。单测覆盖“rotate 后旧密文失效、新密文可解、HTTP 仍可读” |
| 篡改检测 | 靠 GCM authTag；`secrets.json` 被改任一字节，解密抛错，读接口映射为 500（数据可能被篡改），绝不返回脏明文 |
| 读取面 | 仅显式点名可读（`GET …/secrets?name=`），不提供全量导出/列表；`name` 白名单 `[a-zA-Z0-9._-]+`（≤128 字符），创建返回不含 value |
| 损坏处理 | 主密钥长度非法、密文 JSON 非法、条目结构非法一律抛错，拒绝静默重建/静默丢数据 |

## 4. 与 Scriverse credential-vault 的差异

| 维度 | Scriverse | 本模块（dsh-miaowu D5） |
|---|---|---|
| 存储 | SQLite（`providers.encrypted_key` 列） | JSON 文件（`.oh-story/vault/secrets.json`），无本地数据库 |
| 主密钥形态 | `.data/master.key` 存 base64url 字符串，经 `sha256(口令/环境密钥)` 派生 32 字节 | `.oh-story/vault/master.key` 直接存 32 字节随机二进制，无派生（无口令概念） |
| 环境密钥覆盖 | 支持用环境变量直接替代主密钥 | 不支持——开关本身就是环境变量，密钥只认文件，避免“密钥来源”再分叉 |
| 管理面 | 有供应商管理页（并发/RPM/配额/连接测试） | 无 UI 管理页，只有 5 个 HTTP 端点（status/增/查/删/rotate） |
| 平台集成 | 平台级密钥派生与成本估算联动 | 无；纯工作区本地模块 |
| 轮换 | 未强调 | 一等公民：纯函数 `rotateVaultSecrets` + 落盘 `rotateVaultFiles`（备份+回滚），单测覆盖 |

照搬的是思路（主密钥文件 + AES-GCM + 随机 IV + authTag），不是代码。

## 5. 启用步骤

1. 启动 DSH 前设置环境变量：`DSH_MIAOWU_VAULT_ENABLED=1`（模块每次请求读取一次 `process.env`，
   无需重启外只改此变量即生效/失效）。
2. 确认 `services/index.ts` 已加 `import "./vault.js";`（挂载路由；未开启时行为无变化）。
3. 首次写入即建密钥：`POST /oh-story/vault/secrets`（`{ "name": "…", "value": "…" }`），
   成功后 `.oh-story/vault/` 下出现 `master.key` + `secrets.json`。
4. 命名建议：`{供应商}.{用途}`，如 `mimo.tts-key`、`fish.session-token`；只用白名单字符；
   一个 name 一条凭据，覆盖写即轮换该条。
5. 用 `GET /oh-story/vault/status` 验证 `{ enabled: true, ready: true }`
  （`ready` = 主密钥可读写；写前为 `false`，属正常）。
6. 定期 `POST /oh-story/vault/rotate`（如人员/机器交接后），rotate 前建议先确认全部条目可读。

## 6. 结论与后续

- **结论**：保险库作为 opt-in 模块已就绪，默认关闭语义由开关纯函数 + 路由前置检查 +
  “未启用不落盘”单测三重保证；现有凭据路径零影响。是否启用由使用者按 §2 场景自行决定，
  不启用则等价于不存在。
- **已知限制**：无口令派生（密钥即文件）、无 UI 管理面板、文件权限在 Windows 下仅尽力、
  无远程加密备份、损坏文件只报错不自愈。
- **后续（按需，不做 over-engineering）**：
  1. 若要进工作台 UI：加只读状态 + 点名读取面板（仍不做全量导出）；
  2. 若安全要求升级：引入口令 + KDF（scrypt）派生主密钥，或接系统钥匙串；
  3. 若要平台集成：再谈与 DSH 配置/供应商管理的联动，在此之前保持本地模块边界。
