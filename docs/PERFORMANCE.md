# 性能与规模基准（P2-B 骨架）

`scripts/perf-scale.mjs` 是一个可重复的合成基准：它在一个临时工作区里生成 1000 章正文、10000 个大纲/设定/参考资料文件和三份 `.oh-story` 状态文件，然后测量插件实际会用到的**原始文件系统与 JSON 原语**耗时。

> **这不是插件级 SLO 验收，也不是发布门禁。** 它不加载打包后的插件 UI，不经过 DSH fs 缝、HTTP 路由、React 渲染或浏览器绘制，因此不能据此宣称“插件 SLO 通过”。真正的 UI/SLO 证据仍需打包冒烟（`pnpm test:dsh` / `pnpm test:dsh:rc`）或额外的主机级 UI 计时工装。

## 运行方式

```bash
# 完整规模 + 预算断言（JSON，适合记录/对比）
node scripts/perf-scale.mjs --assert --json

# 完整规模 + 预算断言（人类可读摘要）
node scripts/perf-scale.mjs --assert

# 小规模（20 章 / 200 个支持文件），只用于测试工装本身
node scripts/perf-scale.mjs --scale small --assert --json

# 工装测试：不跑 1M 字符完整规模
node --test scripts/perf-scale.test.mjs
```

### 参数

| 参数 | 行为 |
| --- | --- |
| `--root <dir>` | 复用或创建指定目录。目录不存在则创建；为空则生成；已有 `.perf-scale.json` 且规模匹配则直接复用；非空但没有标记、或标记规模不匹配时**拒绝运行**（避免把合成语料混进真实目录）。显式 `--root` 永不被脚本删除。 |
| `--keep` | 保留临时目录（仅对默认 OS 临时目录生效）。 |
| `--assert` | 按原始原语预算判定；超预算退出码 1。不加时仍会报告预算状态，但不据此失败。 |
| `--json` | stdout 只输出一份 JSON 报告。 |
| `--scale <full\|small>` | `full` 为正式语料；`small`（20 章/200 支持文件）只用于测试 CLI 与报告形状，预算不随规模缩小，**不可当作性能结论**。 |
| `--help`, `-h` | 打印用法并退出 0。 |

显式 `--root` 若在生成中途失败，脚本不会删除该目录，可能留下部分文件；手动删除后重跑即可。默认临时目录在同类失败时会自动清理（`--keep` 除外）。

### 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 未加 `--assert`，或所有原始预算通过 |
| `1` | 加了 `--assert` 且有测量超出预算 |
| `2` | 用法错误、生成/校验/读取失败、显式 `--root` 不安全、临时目录清理失败 |

默认（不带 `--root`）使用 `os.tmpdir()` 下的 `dsh-perf-scale-*`，成功后删除；带 `--keep` 时保留并在报告中给出路径。生成、测量均不访问网络、不调用模型；默认只写 OS 临时目录，不写仓库和 `~/.dsh`。

## 合成语料

`full` 规模的内容与规模：

| 区域 | 数量 | 规模（本次实测） |
| --- | --- | --- |
| `正文/第0001章_草稿.md` … `第1000章_草稿.md` | 1000 个 Markdown | 每章 1000 个汉字 + 20 个换行；总 1,000,000 汉字 / 1,020,000 字符 / 3,020,000 UTF-8 字节 |
| `大纲/` | 4000 个小文件（80% `.md`、20% `.json`），每 100 个一组放入子目录 | 与设定、参考资料合计 10,000 个文件、1,996,000 UTF-8 字节 |
| `设定/` | 3000 个 | 同上 |
| `参考资料/` | 3000 个 | 同上 |
| `.oh-story/shelf.json` | 100 条书架记录 | 三份状态文件合计 294,802 字节 |
| `.oh-story/foreshadows.json` | 200 条伏笔 | 同上 |
| `.oh-story/tasks/runs.json` | 200 条 run（顶层数组，含步骤/事件/检查点） | 单文件 170,161 字节 |

创作树文本合计 11,000 个文件 / 5,016,000 UTF-8 字节；整个工作区约 5.3 MB（5.1 MiB）。根目录的 `.perf-scale.json` 是复用标记，最后写入，缺失说明生成未完成。

`small` 规模为 20 章 / 200 个支持文件 / 10 条书架 / 20 条伏笔 / 20 条 run，章密度与状态结构保持不变，供 `node --test scripts/perf-scale.test.mjs` 使用。

## 测量项

除 `read-hash-1m` 取 5 次中位数（`iterations: 5`，`details.samplesMs` 保留原始样本）外，其余每项只跑 1 次（`iterations: 1`）；生成耗时不计入任何测量。路径来自实际生成的语料，并在计时后校验数量/字符数，语料不完整会以退出码 2 失败，而不是静默给出空测量。

| id | 测量内容 | 原始预算 |
| --- | --- | --- |
| `walk-support-10k` | 递归遍历 `大纲/`、`设定/`、`参考资料/`，只数文件，不排序、不 stat | 2000 ms |
| `chapters-1000` | `readdir(正文)` + 过滤章节名 + 逐文件 `stat` 取大小（含按文件名排序） | 500 ms |
| `read-chapters-1m` | 顺序读取 1000 章、拼接，校验 1,020,000 字符 / 1,000,000 汉字 / 3,020,000 字节 | 无（作为 hash 基线） |
| `hash-1m` | 对拼接结果做 SHA-256（UTF-8） | 无 |
| `read-hash-1m` | 再顺序读一遍并在读取时增量 SHA-256，要求与 `hash-1m` 摘要一致 | 500 ms |
| `json-200-runs` | 对 `runs.json` 做 `JSON.parse` + `JSON.stringify`（文件读取不计时） | 无 |
| `backup-collect` | 备份式收集 `正文/大纲/设定/参考资料`：遍历、过滤 `.md/.txt/.json/.jsonl`、按路径排序、顺序读取全部文本，统计文件数与字节数 | 30000 ms |

`backup-collect` 刻意读取**全部** 11,000 个文本文件，不套用备份服务的 2000 文件上限，也没有逐文件 32 MB 上限；它测量的是“遍历 + 读取”原语，不是备份产物的 hash/序列化/落盘。

## 原始预算 vs 路线图 UI SLO

本脚本的预算是**原语上限**，用于发现数量级退化；它们不是产品 SLO，也不覆盖 UI。

| 路线图目标（UI/产品口径） | 本脚本对应项 | 关系与差距 |
| --- | --- | --- |
| 全文检索 < 2 s（约 10 万字符） | 无直接对应；`read+hash 1M 字符 < 500 ms` 只是检索链路的输入原语 | 检索自身的索引、路由、CJK/拼音匹配由 `packages/dsh-plugin/tests/search.test.ts` 的 ~100 KB / 2 s 冒烟覆盖。本脚本不测检索，也不宣称检索 SLO 通过。 |
| 文件树刷新 < 500 ms | `walk-support-10k < 2000 ms`（纯遍历） | 本项不含 DSH fs 缝、权限校验、排序后的树构建、React 渲染与浏览器绘制。产品行为是会话运行期间约每 4 秒安静重列（见 `README.md` / `docs/FORK-FEATURES.md`），仓库内没有 UI 刷新耗时自动测试。 |
| 备份 < 30 s / 100 MB | `backup-collect < 30000 ms` | 语料仅约 5 MB，且不生成备份 JSON、不算 bundle hash、不写文件；30 s 只是该语料的预算上限，**不能替代 100 MB 验收**。 |
| 浏览器包 600 KB | 不在本脚本内 | 由现有构建门禁 `scripts/build-dsh-plugin.ts` 检查（`clientBytes > 600_000` 即失败）。`docs/VALIDATION.md` 记录的最近一次为 399,864 字节（2026-10-24；构建期 CSS minify + UTF-8 输出）。 |

### 明确缺口

要把这些数字升级为“插件级 SLO”，至少还需要：

- **DSH fs 缝**：`resolve` / `contains` / `listDir` / `stat` / `readVersionedFile` 的封装与安全校验开销。
- **HTTP/工作台链路**：`/oh-story` 路由、会话与工作区校验、JSON 校验、搜索索引写入、备份 bundle 的 hash/序列化/落盘。
- **浏览器侧**：文件树构建与渲染、编辑器打开大文件、搜索面板、备份面板的交互延迟、浏览器绘制与主线程占用。
- **打包形态**：通过 npm tarball 安装到隔离 DSH home 后的真实插件，而不是源码直跑。

现有可用证据是**功能集成**：`pnpm test:dsh`（DSH 0.2.1-rc.3）与 `pnpm test:dsh:rc`（DSH 0.2.0-rc.2）的打包冒烟；它验证路由、面板和工具链可用，但不测上述 UI 耗时。UI 计时仍需主机级工装（例如 Playwright 驱动打包插件并记录导航/刷新/搜索耗时），目前仓库内没有该工装，属于后续工作。

### 复跑与失败观测

同一机器上的后续完整复跑（均使用相同命令，除首轮 JSON 外为人类可读摘要）：

| 复跑 | walk | chapters | read | hash | read-hash | json | backup | 结果 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 第 1 次 | 51.3 | 96.5 | 483.4 | 10.4 | 441.8 | 3.0 | 4074.0 | 通过（exit 0） |
| 第 2 次 | 50.0 | 85.8 | 424.7 | 10.6 | 407.4 | 2.9 | 3289.7 | 通过（exit 0） |
| 最终代码复核 | 55.3 | 94.7 | 503.5 | 12.4 | **537.32** | 3.8 | 4284.6 | **失败（exit 1）** |

单位为 ms。最终复核中只有 `read-hash-1m` 超过 500 ms 预算，其余三项通过；`read-chapters-1m` 没有预算，但其 503.5 ms 也说明同一底层成本已接近/超过 500 ms。

结论：`read-hash-1m` 在本机 353–537 ms 间波动，500 ms 预算对“Windows 上顺序打开并读取 1000 个文件”偏紧，**偶发超预算是真实观测**。脚本按设计输出 `perf-scale: FAIL` 并退出 1，不把失败改写成通过。首轮基线表和这次失败复核都应保留，不能只引用通过的那几次。2026-10-24 已按原建议把 `read-hash-1m` 改为 5 次中位数口径，预算仍为 500 ms；见下方「2026-10-24 read-hash 统计口径修正」。

### 2026-10-24 read-hash 统计口径修正

- 决策：`read-hash-1m` 单次墙钟对系统负载和杀毒扫描过于敏感；改为同一进程内连续跑 5 次、取中位数判定，预算保持 500 ms 不变（不放宽预算）。`details.samplesMs` 保留 5 个原始样本，报告仍只有 `iterations` / `ms` 两个判定字段。
- 本机复核：`node scripts/perf-scale.mjs --assert --json` 退出 0；中位数 **314.60 ms**，样本 `[279.96, 320.84, 314.60, 287.12, 331.67]` ms，压缩后语料校验仍与 `hash-1m` 摘要一致。该次复跑与 2026-10-21 的 537.32 ms 单次失败不是同一统计口径，两者都保留，不能互相覆盖。
- 边界：中位数降低单次抖动造成的假失败，但不改变原始原语成本，也不构成插件 UI SLO；`--scale small` 仍不能用于性能结论。

测试基线：`node --test scripts/perf-scale.test.mjs` 6/6 通过，约 2 s；只覆盖小规模生成、报告形状、`--assert` 通过和小规模清理行为，不跑完整 1M 规模。

### 机器与口径警告

- 以上是**热缓存、本机**的单次墙钟时间，不代表其他机器、CI 容器、冷缓存或同机并发负载下的表现；不要跨机比较绝对值。
- `read-hash-1m` 已实测到超预算；该预算接近本机 1000 次顺序文件打开的成本，结果对系统负载和杀毒扫描敏感。
- 生成耗时、Node 启动时间、垃圾回收抖动均未单独统计；`--json` 报告中的 `generatedAt`、`runtime` 用于追溯。
- 全量语料只有约 5 MB，与 100 MB 备份目标不在同一量级。
- 数字只说明原始原语没有数量级退化，不构成“插件 SLO 已通过”的证据。

## 维护约定

- 调整预算必须同时改 `scripts/perf-scale.mjs` 的 `BUDGETS` 与本文件，并重跑一次完整规模记录新基线。
- 完整规模基准（`perf-scale.mjs`）不加入 `pnpm verify`、CI 或发布门禁；只有小规模工装测试 `scripts/perf-scale.test.mjs` 随 `pnpm verify` 运行，防止脚本形状回归。它不产生性能结论。
- `--scale small` 只服务于工装测试，禁止用它得出性能结论。
- 若未来补上主机级 UI 计时工装，应新增独立文档/证据，不把本脚本的原始数字改写成 UI SLO。
