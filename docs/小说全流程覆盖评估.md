# 小说全流程覆盖评估

> 评估对象：`packages/knowledge/oh-story`（钉住上游 Oh Story v0.7.9，manifest 锁定 commit `5de060f9`）
> 评估日期：2026-09-05 · 方式：只读勘察 13 个 skill + 7 个 role + references 资产
> 背景：核查 dsh-miaowu 的小说全流程（拆书/拆解分析/世界观构建/创作整套流程）是否完善，并对照参考项目（NarraLume / Scriverse）的拆解能力定位差距

---

## 1 结论先行

- **核心创作闭环完整**：从扫榜选题 → 拆书 → 建书（世界观/人设/大纲）→ 创作（长篇/短篇）→ 审稿 → 去 AI 味 → 封面 → 存量书导入，每个环节都有明确 skill、方法论参考库、角色分工与确定性校验脚本。
- **拆书维度不缺**：长篇拆解管道（Stage 0-6）与短篇拆解（Stage 2-6）的维度体系（40+ 参考文件、32 题材卡）在规模上超过参考项目 NarraLume 的结构化拆解（12 大类字段）与 Scriverse 的世界观维度分析。
- **真实差距在形态**：oh-story 拆书产物是 Markdown 文档树（人读友好），而参考项目是结构化数据（实体/关系/时间线可查询、证据引用可追溯、世界观指标可量化）。→ 对应待开发清单的「拆书结果结构化」项。
- **明确断档 3 处**：① 独立世界观构建入口（现并入建书 Phase 2）；② 出版/投稿/发行执行；③ 完结/收尾专项结算。均为外围环节，不影响创作主链。

## 3 拆书维度对比（oh-story vs 参考项目）

| 维度 | oh-story（当前） | NarraLume | Scriverse |
|---|---|---|---|
| 形态 | Markdown 文档树（拆文库/{书名}/） | 结构化 JSON（ImportAnalysis） | 正文内审计 + 指标 |
| 主要维度 | 黄金三章/逐章公式/节奏/情绪模块/爽点循环/伏笔地图/冲突升级/循环单元/读者需求/桥段标签/设定（世界观·势力·金手指）/角色档案·关系/文风 | 概要/主题/受众/语气边界/实体/关系/时间线/伏笔/角色弧/场景/风格档案/写作 Skill（12 大类） | 世界观维度（自然/社会/历史/科技/文化）/冲突/待确认问题/覆盖章节 |
| 证据引用 | 位置行号（review 统一 Findings location） | 强制 `[P#]` 原文段号 evidenceParagraphs | 行 ID 锚定 + 行级批注 |
| 可查询性 | 无结构化查询（全文检索为待开发项） | 结构化可查询（实体/关系/时间线库） | FTS5 trigram + 拼音双通道 |
| 定位 | 爆款拆书（市场方法论） | 自有旧稿导入入库（candidate 候选制） | 写作过程审计/管理 |

## 4 断档与差距清单

1. **独立世界观构建入口（P1）**：现并入 `story-long-write` Phase 2 与 `story-architect` 角色，无独立 skill/命令；世界观条目散于 `设定/世界观/`、`设定/势力/`，缺"先建世界观再开书"的独立工作流。
2. **拆书结果结构化（P1）**：拆文库为 Markdown 树，不可查询/不可追溯；参考项目已验证结构化（实体/关系/时间线可检索 + 证据引用）的价值。
3. 出版/投稿/发行执行（P2）：仅参考资料（publishing-guide / submission-craft / short-format），无执行入口。
4. 完结/收尾专项（P2）：长篇收尾只有日更/大修与 review 覆盖，无完结结算流程。
5. 改编环节（P3）：有声/漫画/翻译/版权签约无对应入口。
6. 引用悬空点（P3）：`story` skill 引用的 `scripts/dashboard-server.mjs` 不在 manifest/本地文件清单中。✅ 已核实（2026-09-05）：上游源树与本地 fork 均无此文件（上游刻意排除，短剧侧 `dashboard_server.py` 同模式），`/story dashboard` 在任何环境均无法定位脚本；处置=回馈上游。

## 5 与待开发清单的衔接
